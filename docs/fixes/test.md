
  A. Per-validation vs per-artifact-evidence testament granularity

  Each validation produces a testament containing its result artifact. So if artifact A1 has 3
  validations targeting it, those run in parallel and produce 3 separate validation-result
  testaments — each with ClaimID = original claim, each containing one result artifact.
  Confirming: per-validation granularity, not per-artifact-evidence-bundle?

  MY FEEDBACK: No. When we execute a claims validations, each validation produces a result artifact. The result artifact from each claim's validations is then tied to a parent testament for *all validations tied to that claim*.

  B. Validation-result testaments' own lifecycle

  A validation-result testament goes through the testament lifecycle (generated → posted →
  received → validating → validated). But the original claim's validations target the original
  artifacts by name (A1, A2…), not the result artifacts (R1, R2…). So no validation in the
  registered set targets the result artifacts.

  Two paths:
  - Result-bearing artifacts (those produced by validators) skip validating and go straight
  received → validated since no validation targets them by name.
  - They stay at received as a terminal state (the lifecycle accommodates "no validations
  targeting me" as a fine final state).

  Which? I'd lean toward the first for symmetry (every artifact reaches validated or a failure
  state), but the second is also defensible. Your call.

  MY FEEDBACK: These artifacts remain at published/generated/etc., not received. They have not bee received or validated by any consuming agent.

  C. Self-issuance of validation testaments

  The validation-result testament is issued by the claimant (since the claimant ran the
  validator), and its ClaimID is the original claim (which the claimant issued). So the
  claimant is both issuer and testifier on this testament. Does the lifecycle compress here
  (claimant doesn't need to "receive" their own testament — it's auto-received on commit), or
  do we run the full lifecycle for uniformity?

  I'd lean toward uniformity: run the full lifecycle, with the testament going generated →
  posted → received in essentially one transaction since the claimant is on both ends. But the
  received commit is still explicit so the WAL reflects it.

  MY FEEDBACK: The lifecycle does not compress. The testament remains in published, like its artifacts.

  D. Receipt timing window

  Generated-but-unattached: the claimant can mark received. Once attached: can the claimant
  mark received then (if they didn't see the artifact in the unattached window)? Or is received
   a one-shot that fires the first time the claimant observes the artifact, regardless of
  whether it's attached or not?

  I'd assume one-shot, idempotent — once received, it's received. But want to confirm.

  MY FEEDBACK: The claimant would mark the artifact received when unattatched, then mark the *testament* as received once the testament is submitted. This also means we need to revise our lifecycle. Artifacts now go from received -> attatched, not attatched -> received. `attatched` NOW signifies that the artifact has been received by the claimant and attatched to a testament generated by the target.
